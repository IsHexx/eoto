# eoto 用户画像

本文档定义 `eoto` 的目标客户企业与用户角色。产品设计、权限设计与商业交付必须以本文档为准。

---

## 一、目标客户企业

### 1. 企业特征

`eoto` 第一批目标客户企业具备以下特征：

- **企业规模**：员工人数 20 至 200 人。
- **所属行业**：第一批只选择一个行业，候选行业为代理记账、商贸批发与分销。
- **业务形态**：销售实物商品或标准化专业服务，涉及报价、签约、履约与回款。
- **协同工具**：已经使用钉钉、飞书或企业微信。
- **信息化现状**：没有专职 IT 团队，仍使用表格与聊天记录管理业务。
- **采购决策**：经营者亲自决策软件采购，决策周期短。

首个行业的选择依据见 [项目立项与战略决策纪要](./项目立项与战略决策纪要.md)。

### 2. 候选行业场景

| 行业 | 典型业务 | 核心痛点 | 履约类型 |
| :--- | :--- | :--- | :--- |
| 代理记账 | 销售服务套餐、签订年度服务合同、按月交付核算报税服务、到期续费 | 客户数量多且续费易遗漏、服务费逾期、履约进度不透明、单个客户服务毛利不清楚 | 服务履约 |
| 商贸批发与分销 | 多 SKU 报价、批量下单、分批发货、账期结算 | 报价慢、库存不准、应收账款逾期、单笔订单毛利不清楚 | 实物履约 |

### 3. 代理记账企业的产品边界

代理记账企业为其客户提供核算报税服务。`eoto` 只管理代理记账企业自身的经营业务，包括以下内容：

- 使用 `eoto Sales` 管理服务套餐报价、服务合同与续费提醒。
- 使用 `eoto Flow` 的服务履约跟踪每个客户的月度服务任务。
- 使用 `eoto Cash` 管理服务费应收、催款提醒与单个客户服务毛利。

> [!CAUTION]
> **严禁将 `eoto` 扩展为代理记账企业的核算报税工具。** 代理记账企业为其客户核算报税时，必须继续使用外部会计软件。

### 4. 后续扩展行业

轻工业与加工制造企业需要物料清单与委外加工能力。团队将该行业列为后续扩展行业，通过行业模板接入。

### 5. 不在范围内的企业

以下企业不属于目标客户企业：

- 员工人数超过 1000 人的集团企业。
- 以门店零售为主的 B2C 企业。
- 需要复杂生产排程（MES）的离散制造企业。

## 二、用户角色总览

`eoto` 的用户角色分为两类：

- **客户侧角色**：目标客户企业内部的员工。
- **交付侧角色**：为客户交付与扩展 `eoto` 的人员。

| 用户角色 | 所属类别 | 是否为购买决策者 | 主要交互入口 |
| :--- | :--- | :--- | :--- |
| 经营者 | 客户侧 | 是 | 协同入口平台对话、核心看板 |
| 销售人员 | 客户侧 | 否 | 协同入口平台对话 |
| 采购与仓库人员 | 客户侧 | 否 | 协同入口平台对话、审批确认页 |
| 服务交付人员 | 客户侧 | 否 | 协同入口平台对话 |
| 财务人员 | 客户侧 | 影响决策 | 协同入口平台对话、数据总览 |
| 部门负责人 | 客户侧 | 影响决策 | 协同入口平台审批流 |
| 企业管理员 | 客户侧 | 否 | 管理后台 |
| 前线部署工程师 | 交付侧 | 否 | `eoto Studio` |
| 插件开发者 | 交付侧 | 否 | `eoto Studio SDK` |

### 一人多角色

20 至 50 人的企业中，一名员工经常同时承担多个用户角色。例如经营者兼任部门负责人，或者财务人员兼任采购人员。

> [!IMPORTANT]
> **必须支持一名员工绑定多个用户角色。** 权限设计不得假设每名员工只对应一个用户角色。

## 三、经营者与销售人员的利益关系

经营者与销售人员对客户数据的诉求存在差异：

- **经营者**：希望客户资产归属企业，避免客户随销售人员离职流失。
- **销售人员**：关注个人业绩，不愿意为企业承担额外的录入工作。

团队判断销售人员愿意使用 `eoto Sales`。为了保持这一前提，产品设计必须遵守以下要求：

1. 面向销售人员的每项功能必须直接减少销售人员的工作量。
2. 系统自动录入客户跟进记录，不要求销售人员手动填写表单。
3. 系统为销售人员提供报价生成、库存查询与回访提醒等直接收益。

## 四、客户侧用户画像

### 1. 经营者

- **角色定位**：企业所有者或总经理，负责购买 `eoto` 并承担经营结果。
- **典型特征**：
  - 同时关注销售、履约与资金，日常时间分散。
  - 主要在手机上通过协同入口平台处理工作。
  - 不愿学习复杂软件，偏好直接提问并获得结论。
- **核心诉求**：
  - 随时了解每笔订单是否成交、是否完成履约、是否回款、是否盈利。
  - 掌握客户资产，避免客户随销售人员离职流失。
- **主要使用产品**：`eoto Core`、`eoto Cash`、`eoto Sales`。
- **高危操作职责**：确认大额付款登记与核心审批。

### 2. 销售人员

- **角色定位**：负责获取线索、跟进客户、报价与签约。
- **典型特征**：
  - 大部分时间在外拜访客户或在线沟通。
  - 不愿手动录入客户跟进记录。
  - 业绩考核直接关联签约与回款。
- **核心诉求**：
  - 自动从聊天与语音中录入客户跟进记录。
  - 快速生成准确报价单。
  - 报价前确认库存或服务排期。
  - 按时收到回访与续费提醒。
- **主要使用产品**：`eoto Sales`。

### 3. 采购与仓库人员

- **角色定位**：在商贸批发与分销企业中负责采购下单、入库、出库与发货。
- **典型特征**：
  - 依赖表格记录库存。
  - 经常接到销售人员询问库存与发货进度。
- **核心诉求**：
  - 签约后系统自动锁定库存。
  - 库存不足时系统自动生成采购建议。
  - 减少重复回答库存查询。
- **主要使用产品**：`eoto Flow`（实物履约）。
- **高危操作职责**：确认库存红线操作，例如库存调整与退单入库。

### 4. 服务交付人员

- **角色定位**：在代理记账企业中为客户交付月度核算报税服务，通常由记账会计担任。
- **典型特征**：
  - 每人同时服务数十家客户。
  - 每月按固定节点收集票据、核算、报税并向客户交付报表。
  - 使用外部会计软件完成核算报税操作。
- **核心诉求**：
  - 查看每个客户的本月服务任务进度。
  - 系统自动提醒客户提交票据。
  - 减少重复回答客户的进度查询。
- **主要使用产品**：`eoto Flow`（服务履约）。

### 5. 财务人员

- **角色定位**：负责应收应付、收付款登记与对账，通常由出纳或会计担任。
- **典型特征**：
  - 使用外部会计软件处理核算报税。
  - 每月花费大量时间核对客户回款与供应商付款。
- **核心诉求**：
  - 自动核对订单与资金流水。
  - 系统自动提醒逾期客户付款。
  - 按标准格式导出数据至外部会计软件。
- **主要使用产品**：`eoto Cash`。
- **高危操作职责**：在经营者授权范围内确认付款登记。

### 6. 部门负责人

- **角色定位**：销售主管、仓库主管、交付主管等中层管理人员。
- **典型特征**：
  - 需要审批本部门的报价折扣、采购申请与费用。
  - 需要掌握本部门员工的工作进度。
- **核心诉求**：
  - 在协同入口平台中直接处理审批流。
  - 查看本部门业绩与待办事项。
- **主要使用产品**：`eoto Link`、`eoto Sales`、`eoto Flow`。

### 7. 企业管理员

- **角色定位**：负责为企业开通 `eoto`、绑定协同入口平台并分配权限。
- **典型特征**：
  - 中小企业通常由行政人员或经营者兼任，不具备专业 IT 能力。
- **核心诉求**：
  - 一次授权即可同步员工与部门。
  - 选择行业模板后直接开始使用。
  - 按岗位分配权限，无需逐项配置。
- **主要使用产品**：`eoto Link`、管理后台。

## 五、交付侧用户画像

### 1. 前线部署工程师

- **角色定位**：负责构建行业模板，并为每个行业的首批客户企业提供驻场支持。
- **典型特征**：
  - 熟悉目标行业业务，具备基础技术能力。
  - 不为单个客户企业提供长期定制服务。
- **核心诉求**：
  - 在 `eoto Studio` 中构建与维护行业模板。
  - 从首批客户企业收集反馈并完善行业模板。
  - 无需修改底层主干源码即可满足行业需求。
- **主要使用产品**：`eoto Studio`。

### 2. 插件开发者

- **角色定位**：为特定行业开发 `eoto Studio` 行业插件的开发人员。
- **典型特征**：
  - 第一批插件开发者来自 `eoto` 团队。
  - 熟悉 API 与 MCP 等标准接口。
- **核心诉求**：
  - 获得稳定的契约版本与清晰的接口文档。
  - 在本地测试插件，再发布到 `eoto Studio`。
- **主要使用产品**：`eoto Studio SDK`。

## 六、人工确认职责分配

> [!CAUTION]
> **必须由授权角色确认所有资金登记、库存红线操作与核心审批。** 以下分配为初始方案，最终权限以 RBAC 设计文档为准。

| 高危操作 | 默认确认角色 | 可授权的确认角色 |
| :--- | :--- | :--- |
| 登记供应商付款 | 经营者 | 财务人员（限额内） |
| 退款与退单 | 经营者 | 部门负责人（限额内） |
| 库存调整与盘点差异处理 | 采购与仓库人员 | 部门负责人 |
| 超权限报价折扣 | 部门负责人 | 经营者 |

---

## 七、主数据模型设计输入

主数据模型设计必须满足以下要求：

1. 商品实体必须同时支持实物商品与服务类商品。服务类商品不占用库存。
2. 订单实体必须支持按月、按季或按年收费的周期性服务合同。
3. 员工实体必须支持绑定多个用户角色。

---

## 八、待确认事项

以下事项需要在后续设计中确认：

1. 首个接入的协同入口平台。
2. 经营者授权财务人员确认付款登记的默认限额。
3. 企业管理员是否需要独立的管理后台，或者通过协同入口平台完成全部配置。
4. 插件开发者是否向合作伙伴开放。
