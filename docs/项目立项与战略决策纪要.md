# eoto 项目立项与战略决策纪要

本文档记录 `eoto` 的问题定义、产品定义、架构原则、高危底线、商业交付策略、范围取舍与演进阶段。所有研发与商业决策必须遵循本文档确立的边界。

---

## 一、问题定义

### 1. 市场痛点

当前企业 AI 落地存在以下两类核心痛点：

- **企业 AI 落地浮于表面**：大量前线部署工程师（FDE）进入企业后，只能交付外挂式知识库问答。这类方案无法触达核心业务。企业因此难以说明 AI 的实际业务价值。
- **基础软件数据孤岛严重**：企业的 CRM、ERP 与财务软件彼此割裂。业务数据分散在表格、聊天记录与多套软件中，跨部门流转依赖人工传递。

### 2. 经营者的根本问题

中小企业经营者缺少的不是软件，而是对每一笔订单的确定性。企业对客户的每个报价与合同，都要经过多名员工接力完成。信息在传递中丢失，经营者只能逐个询问员工才能了解以下四个问题：

1. 这笔订单是否成交。
2. 这笔订单是否完成履约。
3. 这笔订单的款项是否收回。
4. 这笔订单是否盈利。

`eoto` 的产品目标是让经营者随时获得这四个问题的准确答案，并让 AI 主动推进每笔订单的下一步。

## 二、产品定义

### 1. 三个独立子系统

`eoto` 由三个独立子系统组成。子系统按管理对象划分：

| 子系统 | 产品名称 | 管理对象 | 核心职责 |
| :--- | :--- | :--- | :--- |
| CRM 子系统 | `eoto Sales` | 人：客户及客户交易 | 线索、客户、跟进记录、报价、合同、销售订单与续费 |
| ERP 子系统 | `eoto Flow` | 物：商品及其流转 | 商品、采购、库存、出库与发货、服务履约 |
| 经营财务子系统 | `eoto Cash` | 钱：资金对象 | 应收应付、收款登记、催款提醒、单笔订单毛利与现金流预测 |

划分管理对象时，遵守以下规则：

- **对象归属唯一**：每类业务对象只归一个子系统管理。与客户的交易记录归 CRM 子系统，包括报价、合同与销售订单。物品的流转归 ERP 子系统，包括采购、库存、出库与发货。
- **金额属性可以共用**：报价金额、合同金额、订单金额与商品成本是业务对象的属性，可以出现在任何子系统中。
- **资金对象只归经营财务子系统**：回款计划、应收、收款、付款与资金流水只由经营财务子系统写入。其他子系统通过对外接口读取并显示。

每个子系统包含以下四个部分：

- **独立数据库**：只存放本子系统持有的数据。
- **业务状态机**：控制本子系统业务实体的状态流转。
- **子 Agent**：操作本子系统的业务。
- **对外接口**：本子系统与外部交互的唯一出口。

### 2. 子系统交互规则

子系统之间按以下规则交互：

- **唯一出口**：子系统之间、`eoto Core` 与子系统之间只能通过对外接口交互。
- **接口组成**：对外接口包含 API、MCP 工具与领域事件，统一定义在契约规范中。
- **事件联动**：子系统通过领域事件通知其他子系统。例如 CRM 子系统签约并创建销售订单后，发布订单已创建事件。ERP 子系统据此生成服务任务，经营财务子系统据此生成回款计划。
- **主数据归属**：每个主数据实体只由一个子系统持有与写入。其他子系统通过实体 ID 引用该实体，并通过持有方的对外接口读取。

主数据实体的初始归属方案如下：

| 主数据实体 | 归属方 |
| :--- | :--- |
| 员工 | `eoto Core`（由 `eoto Link` 从协同入口平台同步） |
| 部门 | `eoto Core`（由 `eoto Link` 从协同入口平台同步） |
| 客户 | CRM 子系统 |
| 销售订单 | CRM 子系统 |
| 采购订单 | ERP 子系统 |
| 商品 | ERP 子系统 |
| 资金流水 | 经营财务子系统 |

CRM 子系统持有合同与销售订单。ERP 子系统持有采购订单、出库与发货记录。经营财务子系统通过销售订单 ID 关联回款计划，通过采购订单 ID 关联应付。最终归属在主数据模型设计时确认。

### 3. `eoto Core` 的职责

`eoto Core` 的主 Agent 理解自然语言指令，并拆解跨子系统任务。主 Agent 通过各子系统的对外接口调度子 Agent。`eoto Core` 不直接访问任何子系统的数据库。

### 4. AI 的职责

AI 在 `eoto` 中承担以下三项职责：

1. 将聊天、语音与票据中的非结构化信息转换为订单状态变更。
2. 根据订单状态主动提醒或推进下一步操作。
3. 在执行高危操作前暂停，并请求授权角色确认。

### 5. 履约的两种类型

ERP 子系统支持两种履约类型：

- **实物履约**：查库存、锁定库存、采购、发货与签收。适用于商贸批发与分销企业。
- **服务履约**：按周期生成服务任务、跟踪任务进度并交付成果。适用于代理记账企业。

## 三、架构与研发原则

### 1. 研发模式：用编程 Agent 并行开发，先发布契约

研发团队使用多个编程 Agent 并行开发各子系统。启动并行开发前，研发团队必须解决以下三个问题：

- **发布首个契约版本**：架构师必须先发布主数据模型与契约规范的首个契约版本。主数据模型统一管理七个实体：员工、部门、客户、商品、销售订单、采购订单、资金流水。契约版本必须包含每个子系统的对外接口定义。后续变更必须发布新的契约版本，不得在代码中私自修改。
- **采用单仓库结构**：所有契约规范与产品代码存放在同一个 `eoto` 仓库中。编程 Agent 可以同时读取契约与全部代码，契约变更可以在一次提交中同步到所有代码包。
- **采用轻界面、重引擎的架构**：前端只保留核心看板、审批确认页与数据总览。研发团队将工程重心放在各子系统的业务状态机与对外接口上。

### 2. 高危业务底线

进销存与资金模块的容错率为零。研发与运行阶段必须同时设防：

- **测试防线**：测试 Agent 必须构建并执行自动化集成测试，校验库存并发扣减、退单回滚与资金对账逻辑。
- **运行防线**：系统触发资金登记、库存红线操作或核心审批前，必须暂停并等待授权角色确认。

> [!CAUTION]
> **必须对资金变动、库存红线操作与核心审批强制执行人工确认（Human-in-the-loop）。** 测试 Agent 必须覆盖所有进销存并发扣减、退单回滚与资金对账的自动化集成测试。

> [!CAUTION]
> **严禁 `eoto` 直接执行资金划转。** `eoto Cash` 只登记与提醒收付款。财务人员必须在银行或支付渠道中自行完成付款操作。

### 3. 数据与模型合规

> [!WARNING]
> **必须在取得授权后才能读取聊天数据。** 每个协同入口平台的接入设计必须写明数据获取方式、授权流程与个人信息保护法合规措施。

> [!WARNING]
> **必须使用已完成生成式人工智能服务备案的大模型。** 大模型选型与切换必须经过架构师审查。

## 四、商业交付策略

### 1. 以行业模板替代逐个客户定制

> [!CAUTION]
> **严禁修改底层主干源码来满足单个客户的个性化需求。** 直接修改底层主干源码会导致代码分支失控，使公司沦为低毛利软件外包商。

目标客户企业的规模为 20 至 200 人，年度软件预算有限。逐个客户驻场定制的成本超过客户的付费能力。因此，交付团队采用以下策略：

- **构建行业模板**：前线部署工程师在 `eoto Studio` 中为每个行业构建一次行业模板。同行业客户直接复用该模板。
- **客户自助开通**：企业管理员通过协同入口平台授权开通 `eoto`，并选择所属行业模板。
- **限定驻场范围**：前线部署工程师只为每个行业的首批客户企业提供驻场支持，用于验证与完善行业模板。
- **保持主干标准化**：所有客户运行同一套标准化业务内核，保障全量客户平滑升级。

### 2. 收费模式

`eoto` 采用订阅制收费。定价与单位经济模型尚未确定，团队必须通过客户访谈确定定价区间。

## 五、核心范围取舍

### 1. 放弃自研 OA 与人事（HR）系统

- **决策原因**：钉钉、飞书与企业微信已经覆盖审批、考勤、排班与组织架构等基础功能。企业替换这些功能的意愿极低。
- **替代策略**：`eoto Link` 直接接入钉钉、飞书与企业微信，作为 `eoto Core` 的交互入口。系统调用协同入口平台的现有接口触发审批流。

> [!IMPORTANT]
> **严禁重复自研 OA、HR 与基础协同办公模块。** 所有协同入口与审批流必须通过 `eoto Link` 接入协同入口平台。

### 2. 聚焦经营财务，放弃核算报税

- **放弃领域**：`eoto` 放弃总账、会计凭证与税务申报。核算报税涉及严格的财税合规与法律责任。
- **聚焦领域**：`eoto Cash` 聚焦经营财务，核心能力包括以下四项：
  - 应收应付管理与催款提醒
  - 供应商付款登记与提醒
  - 单笔订单毛利核算
  - 现金流预测
- **报税对接策略**：`eoto Cash` 提供标准导出接口。财务人员按标准格式导出数据，对接外部会计软件。

> [!IMPORTANT]
> **严禁自研总账、会计凭证与税务申报功能。** 核算报税需求仅通过 `eoto Cash` 的标准导出接口对接外部会计软件。

### 3. 优先服务未使用进销存软件的企业

已经使用进销存软件的企业替换意愿较低，原因与放弃 OA 相同。第一批目标客户企业优先选择仍使用表格与聊天管理业务的企业。

## 六、目标客户企业

第一批目标客户企业只选择一个行业。团队从以下两个候选行业中选择首个行业：

| 候选行业 | 优势 | 风险 |
| :--- | :--- | :--- |
| 代理记账 | 没有库存并发风险，完整链路开发周期最短。每家代理记账企业服务大量中小企业，具备渠道价值。 | 核心痛点是核算报税本身，`eoto` 不提供该功能。行业已有专用代账 SaaS。 |
| 商贸批发与分销 | 订单生命周期最完整，最能体现跨环节联动价值。 | 库存并发风险高。部分企业已经使用进销存软件。 |

团队确定首个行业为代理记账。商贸批发与分销为第二个行业的候选。轻工业与加工制造需要物料清单与委外加工，列为后续扩展行业。

第一版的痛点分析与功能范围见 [客户痛点与第一版产品范围](./客户痛点与第一版产品范围.md)。

目标客户企业的详细定义见 [用户画像](./用户画像.md)。

## 七、演进阶段与商业化路线

项目按订单生命周期的覆盖深度划分演进阶段。每个演进阶段都能独立商业化，并持续提升跨环节联动价值。

| 演进阶段 | 核心目标 | 交付范围 |
| :--- | :--- | :--- |
| 基础设施（贯穿全程） | 交互入口与主 Agent | `eoto Link` 接入钉钉、飞书与企业微信。`eoto Core` 提供主 Agent，并通过对外接口调度三个子系统。 |
| 第一阶段 | 首个行业的订单生命周期全链路 | 从聊天中录入客户与报价，签约后跟踪履约进度，到期提醒回款。资金只登记与提醒。 |
| 第二阶段 | 履约深化与第二个行业 | 实物履约增加库存锁定、并发扣减、采购建议与退单回滚。服务履约增加周期任务排程。通过行业模板扩展第二个行业。 |
| 第三阶段 | 经营分析 | `eoto Cash` 增加单笔订单毛利、现金流预测与标准导出接口。`eoto Core` 为经营者提供经营分析建议。 |

`eoto Studio` 贯穿全部演进阶段。前线部署工程师通过 `eoto Studio` 构建与维护行业模板。

## 八、关键假设与验证

### 1. 团队已确认的假设

以下假设由团队判断确认：

- **聊天数据可以获取**：`eoto Link` 可以通过协同入口平台获取销售沟通数据。
- **销售人员愿意使用**：销售人员愿意使用 `eoto Sales` 记录客户跟进。

### 2. 待验证的假设

团队必须通过 10 至 20 家目标客户企业的访谈验证以下假设：

1. 经营者愿意为订单生命周期全链路支付的年费区间。
2. 代理记账企业的现有替代方案与迁移阻力。
3. [客户痛点与第一版产品范围](./客户痛点与第一版产品范围.md) 中的痛点与严重程度。
