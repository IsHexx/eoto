# eoto 项目立项与战略决策纪要

本文档记录 `eoto` 的项目初衷、架构原则、高危底线、商业交付策略、范围取舍与演进阶段。所有研发与商业决策必须遵循本文档确立的边界。

---

## 一、项目初衷与市场洞察

### 1. 市场痛点

当前企业 AI 落地存在以下两类核心痛点：

- **企业 AI 落地浮于表面**：各行各业对 AI 改造需求强烈。但大量前线部署工程师（FDE）进入企业后，只能交付外挂式知识库问答。这类方案无法触达核心业务底层。企业因此难以说明 AI 的实际业务价值，也无法量化投入产出。
- **基础软件数据孤岛严重**：大小企业普遍使用 CRM、OA、财务与 ERP 等基础软件。但传统软件彼此割裂，业务流难以跨系统串联。市场缺乏以 AI 为核心、统一驱动底层业务流的新一代平台。

### 2. 初始构想

团队在立项初期形成以下产品与商业构想：

- **产品形态**：团队最初计划自研 CRM、OA、财务与 ERP 四大基础业务系统。每个子系统内置专属子 Agent，直接操作本系统业务。平台顶层设立 `eoto Core`，统一理解自然语言指令并调度各子 Agent 跨系统协同作业。
- **商业模式**：产品以标准化底座切入企业客户。交付团队结合企业特点微调局部功能，打包销售全套系统。团队同时提供定制化实施与售后服务。

---

## 二、核心推演与架构原则

团队针对“传统研发重、替换成本高、定制易外包化”三大风险展开推演。基于推演结果，项目确立以下研发与交付原则。

### 1. 研发模式：用编程 Agent 并行开发，先立总规矩

AI 编程能力成熟后，代码生成不再是核心瓶颈。研发团队可以使用多个编程 Agent 并行开发各业务模块。启动并行开发前，研发团队必须提前解决以下三个新瓶颈：

- **锁定统一主数据模型与契约规范**：启动并行开发前，架构师必须先锁定全平台共享的主数据模型与契约规范。核心数据库 Schema 统一管理六个主数据实体：员工、部门、客户、商品、订单、资金流水。契约规范统一定义 API 与 MCP 接口，防止各子系统字段割裂与状态不同步。
- **采用轻界面、重引擎的 AI 原生架构**：`eoto Core` 与各子 Agent 主导业务操作。前端不再堆砌传统 ERP 的复杂表单，仅保留核心看板、审批确认页与数据总览。研发团队将工程重心集中在后端业务状态机与标准工具接口上。
- **严守高危业务底线**：进销存与资金流模块的容错率为零，研发与运行阶段必须同时设防。
  - **测试防线**：测试 Agent 必须构建并执行自动化集成测试，全面校验库存并发扣减、退单回滚与资金对账逻辑。
  - **运行防线**：系统在运行态触发资金流转、库存红线操作或核心审批前，必须暂停并等待授权人员确认。

> [!CAUTION]
> **必须对资金变动与核心审批强制执行人工确认（Human-in-the-loop）。** 同时，测试 Agent 必须覆盖所有进销存并发扣减、退单回滚与资金对账的自动化集成测试。

### 2. 商业交付：将定制化从底层主干源码移至 `eoto Studio`

> [!CAUTION]
> **严禁修改底层主干源码来满足单个客户的个性化需求。** 直接修改底层主干源码会导致代码分支失控。分支失控会使测试与维护成本指数级上升，最终让公司沦为低毛利软件外包商。

交付团队必须坚持“标准内核 + `eoto Studio`”架构，兼顾产品标准化与交付灵活性：

- **保持底层主干源码绝对标准化**：所有客户运行同一套标准化业务内核，保障全量客户平滑升级。
- **将客户差异化配置沉淀至 `eoto Studio`**：实施团队在 `eoto Studio` 中配置客户专属 Prompt、业务规则库、工作流与行业插件。特殊审批流、差异化提成算法与行业专属字段全部收敛在这一层。该模式既发挥 AI 极速定制的优势，又避免代码分支腐化。

## 三、核心范围取舍（关键决策）

团队希望避免与巨头正面竞争，并降低客户迁移阻力。为此，项目对最初规划的四大系统做出明确减法与边界重定义。

### 1. 放弃自研 OA 与人事（HR）系统

- **决策原因**：钉钉、飞书与企业微信已经覆盖审批、考勤、排班、入转调离与组织架构等基础功能。这些功能接近免费。自研 OA 与 HR 属于重复造轮子，企业替换意愿极低。
- **替代策略**：`eoto` 不自研 OA 与 HR。`eoto Link` 直接接入钉钉、飞书与企业微信，将其作为 `eoto Core` 的天然交互入口。系统直接调用协同入口平台的现有接口触发审批流，让员工零学习成本上手。

> [!IMPORTANT]
> **严禁重复自研 OA、HR 与基础协同办公模块。** 所有协同入口与审批流必须通过 `eoto Link` 接入外部协同入口平台。

### 2. 重定义财务边界：聚焦经营财务，放弃核算报税

- **放弃领域**：`eoto` 明确放弃总账、会计凭证与税务申报等核算报税领域。金蝶与用友在该领域深耕多年。核算报税涉及严格的财税合规与法律责任，客户难以信任新系统。
- **聚焦领域**：`eoto Cash` 切入经营财务，解决企业经营者日常最关注的利润与资金问题。核心能力包括以下四项：
  - 应收应付管理与自动催款
  - 供应商付款管理
  - 单笔订单毛利核算
  - 现金流预测
- **报税对接策略**：年底报税时，`eoto Cash` 提供标准导出接口。财务人员按标准格式导出数据，无缝对接客户现有的会计软件。

> [!IMPORTANT]
> **严禁自研总账、会计凭证与税务申报功能。** 核算报税需求仅通过 `eoto Cash` 的标准导出接口对接外部会计软件。

## 四、演进阶段与商业化路线

基于上述取舍，项目确立“入口接入、单点破局、数据滚雪球”的三阶段演进策略。每个演进阶段都能独立商业化变现，同时持续提升 `eoto Core` 的协同价值与客户留存率。

| 演进阶段 | 核心产品 | 商业定位 | 核心能力与业务价值 |
| :--- | :--- | :--- | :--- |
| 基础设施（贯穿全程） | `eoto Link` 与 `eoto Core` | 交互入口（替代 OA/HR） | `eoto Link` 接入钉钉、飞书与企业微信。员工在日常协同入口平台直接与 `eoto Core` 对话，降低使用门槛与推广阻力。 |
| 第一阶段 | `eoto Sales` | 单点破局与首桶金 | 离营收最近、付费意愿最强且容错率高。`eoto Sales` 自动从聊天与语音中录入客户跟进、生成报价单并提醒回访。该产品帮销售减负，同时帮经营者管住客户资产。 |
| 第二阶段 | `eoto Flow` | 销售到交付闭环与高留存 | 无缝承接 `eoto Sales` 的签单，管理查库存、锁定库存、采购与发货全流程。`eoto Flow` 完成销售到交付闭环，大幅提高客户替换成本。 |
| 第三阶段 | `eoto Cash` | 高溢价与经营参谋 | 结合前两阶段的合同与成本数据，`eoto Cash` 自动核算应收应付、单笔订单毛利与现金流。`eoto Core` 进化为经营者的 AI 经营参谋。 |

`eoto Studio` 贯穿全部三个演进阶段的商业化交付。实施团队通过 `eoto Studio` 快速配置行业规则与插件。该机制在不触碰底层主干源码的前提下满足个性化需求。
