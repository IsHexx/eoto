# eoto 仓库结构与代码组织规范

本文档定义 `eoto` 的多仓库结构、各仓库职责与跨仓库协作规则。仓库组织方式参照 Model Context Protocol（MCP）的做法：一个主仓库发布规范，多个独立仓库实现规范。

---

## 一、组织原则

`eoto` 采用多仓库结构。各仓库的分工如下：

- **主仓库**：`eoto` 仓库是主仓库。主仓库只存放规范、文档与契约，不存放业务实现代码。
- **产品仓库**：每个子 Agent 与 SDK 使用独立仓库。产品仓库实现主仓库发布的契约规范。
- **单向依赖**：产品仓库依赖主仓库的契约版本。主仓库不依赖任何产品仓库。

---

## 二、仓库清单

| 仓库名称 | 对应产品 | 仓库类型 | 职责 |
| :--- | :--- | :--- | :--- |
| `eoto` | 全平台 | 主仓库 | 存放战略文档、统一术语表、写作规范、主数据模型与契约规范。 |
| `eoto-core` | `eoto Core` | 产品仓库 | 实现自然语言理解、跨系统任务拆解与子 Agent 调度。 |
| `eoto-link` | `eoto Link` | 产品仓库 | 实现钉钉、飞书与企业微信的接入与审批流连接。 |
| `eoto-sales` | `eoto Sales` | 产品仓库 | 实现 CRM 子 Agent 与销售业务状态机。 |
| `eoto-flow` | `eoto Flow` | 产品仓库 | 实现 ERP 子 Agent 与库存、采购、发货业务状态机。 |
| `eoto-cash` | `eoto Cash` | 产品仓库 | 实现经营财务子 Agent、资金流水管理与标准导出接口。 |
| `eoto-studio-sdk` | `eoto Studio SDK` | 产品仓库 | 提供开发 `eoto Studio` 行业插件所需的接口定义、工具库与示例。 |

所有仓库统一托管在同一个 GitHub 账号或组织下。仓库名称统一使用小写字母与连字符。

---

## 三、主仓库目录结构

主仓库按以下目录组织内容：

```text
eoto/
├── AGENTS.md          全仓库协作规矩，所有产品仓库共同遵守
├── README.md          项目总览与仓库导航
├── docs/              战略、产品与规范文档
│   └── standards/     统一术语表与文档写作规范
├── spec/              主数据模型与契约规范，按契约版本分目录存放
└── .agents/           文档治理插件与校验脚本
```

`spec/` 目录在主数据模型锁定后创建。每个契约版本使用日期命名子目录，格式为 `YYYY-MM-DD`。

---

## 四、本地开发目录

开发人员将所有仓库克隆到同一个父目录下，并列存放。本地目录名称与仓库名称保持一致。

```text
Project/
├── eoto/
├── eoto-core/
├── eoto-link/
├── eoto-sales/
├── eoto-flow/
├── eoto-cash/
└── eoto-studio-sdk/
```

## 五、跨仓库协作规则

> [!CAUTION]
> **严禁在产品仓库中私自修改主数据模型或契约规范。** 所有字段与接口变更必须先在主仓库提交并发布新契约版本。

各仓库必须遵守以下规则：

1. **声明契约版本**：每个产品仓库必须在 `README.md` 中声明当前实现的契约版本。
2. **通过契约通信**：产品仓库之间只能通过契约规范定义的 API 与 MCP 接口通信。
3. **禁止跨库读写**：产品仓库严禁直接读写其他产品仓库的数据库。
4. **继承总规矩**：每个产品仓库根目录必须包含 `AGENTS.md`，并引用主仓库的 `AGENTS.md`。
5. **隔离客户定制**：客户定制必须使用 `eoto-studio-sdk` 开发为插件，严禁合入产品仓库的主干分支。
6. **统一术语**：所有仓库的文档与代码注释必须使用主仓库的统一术语表。

---

## 六、契约变更流程

变更主数据模型或契约规范时，按以下步骤执行：

1. 开发人员在主仓库提交变更提案。
2. 架构师审查变更对各产品仓库的影响。
3. 架构师批准后，主仓库发布新的契约版本目录。
4. 各产品仓库升级实现，并更新 `README.md` 中声明的契约版本。
