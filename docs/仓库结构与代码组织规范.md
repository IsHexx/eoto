# eoto 仓库结构与代码组织规范

本文档定义 `eoto` 的仓库结构、目录职责与代码包协作规则。

---

## 一、组织原则

`eoto` 采用单仓库结构。所有文档、契约规范与产品代码存放在同一个 `eoto` 仓库中。

团队选择单仓库结构的原因如下：

- **编程 Agent 效率**：编程 Agent 可以同时读取契约规范与全部代码。
- **契约同步**：契约变更与所有代码包的适配可以在一次提交中完成。
- **团队规模**：当前由一个团队开发一个产品，不存在多个独立的实现方。

> [!NOTE]
> 团队出现外部插件开发者后，将 `packages/studio-sdk/` 拆分为独立仓库 `eoto-studio-sdk`。其他代码包保留在主仓库中。

---

## 二、目录结构

主仓库按以下目录组织内容：

```text
eoto/
├── AGENTS.md            全仓库协作规矩
├── README.md            项目总览与目录导航
├── docs/                规范级文档：战略、产品与架构文档
│   ├── standards/       统一术语表与文档写作规范
│   └── research/        探索级文档：访谈记录、竞品分析与调研笔记
├── spec/                主数据模型与契约规范，按契约版本分目录存放
├── packages/            产品代码
│   ├── core/            eoto Core：主 Agent
│   ├── link/            eoto Link：协同入口平台接入
│   ├── sales/           eoto Sales：CRM 子系统
│   ├── flow/            eoto Flow：ERP 子系统
│   ├── cash/            eoto Cash：经营财务子系统
│   └── studio-sdk/      eoto Studio SDK：行业插件开发工具包
└── .agents/             文档治理插件与校验脚本
```

研发团队在首次需要时创建对应目录。`spec/` 下的每个契约版本使用日期命名子目录，格式为 `YYYY-MM-DD`。

---

## 三、代码包协作规则

> [!CAUTION]
> **严禁在代码包中私自修改主数据模型或契约规范。** 所有字段与接口变更必须先修改 `spec/` 并发布新的契约版本。

各代码包必须遵守以下规则：

1. **只通过对外接口交互**：`core`、`sales`、`flow` 与 `cash` 代码包之间只能调用对方的对外接口，或订阅对方的领域事件。
2. **禁止跨包访问数据库**：每个子系统使用独立数据库。代码包严禁直接读写其他代码包的数据库。
3. **禁止跨包引用内部代码**：代码包只能引用 `spec/` 生成的接口定义，严禁引用其他代码包的内部实现。
4. **隔离客户定制**：客户与行业定制必须使用 `studio-sdk` 开发为行业插件，严禁写入 `packages/` 下的其他代码包。
5. **统一术语**：所有文档与代码注释必须使用统一术语表中的标准术语。

---

## 四、契约变更流程

变更主数据模型或契约规范时，按以下步骤执行：

1. 开发人员在 `spec/` 中提交变更提案。
2. 架构师审查变更对各代码包的影响。
3. 架构师批准后，开发人员发布新的契约版本目录。
4. 开发人员在同一次提交中更新所有受影响的代码包。
