# eoto 受控文档写作规范（ASD-STE100 适配版）

本文档定义 `eoto` 项目所有 Markdown 文档的写作规范。规范基于 ASD-STE100 简化技术英语原则，并适配中文与英文双语技术文档。

所有项目成员与 AI Agent 必须遵守本文档与 [统一术语表.md](./统一术语表.md)。

---

## 一、核心目标与命名语言原则

本文档确保所有项目文档与协作说明达到以下四项标准：

1. **中文文件命名与中文正文**：除 `README.md`、`AGENTS.md`、`SKILL.md` 等行业约定俗成的英文文件名外，项目内所有 Markdown 文档的文件名统一使用中文。正文默认使用中文，其中涉及的专业术语、产品名称、缩写与技术标识符按习惯正常使用英文（如 `eoto`、CRM、ERP、API、MCP、SKU、RBAC、Prompt、Schema）。
2. **术语唯一**：全仓库使用统一名词和统一定义，消除概念歧义。
3. **表达客观精确**：使用标准互联网产品与工程术语，用简短主动句表达清晰动作。禁用比喻、拟人、黑话、情绪化修饰词与空泛修辞。
4. **高危显性**：安全红线与人工确认要求前置显示，防止遗漏关键约束。

---

## 二、用词选择（Word Choice）

编写文档时，遵守以下用词规则：

1. 仅使用 [统一术语表.md](./统一术语表.md) 中经批准的术语、含义与词性。
2. 保持一词一义。不要依赖上下文消除多义词或歧义词。
3. 优先使用标准互联网产品与系统架构术语，禁用比喻、拟人、黑话、情绪化修饰词与空泛修辞。
4. 减少使用双引号。仅在直接引用原文或标识特定字段值时使用引号。
5. 表示动作时，直接使用经批准的动词，不要使用动词派生的名词结构（对应 STE 规则 3.7）。
6. 编写英文内容时，禁止使用由动词和介词组成的短语动词（对应 STE 规则 9.3）。

### 正误示例

| 规则项 | 禁止写法（反例） | 批准写法（正例） |
| :--- | :--- | :--- |
| 禁用比喻与情绪词 | 业务引擎负责管真相、状态与铁律。 | 业务引擎负责主数据持久化、业务状态机流转、业务规则校验与权限控制。 |
| 禁用拟人表达 | 状态变化后，子 Agent 自己醒过来干活。 | 状态变化后，系统通过事件驱动或定时任务自动触发子 Agent 执行。 |
| 禁用黑话 | 订单跨三个模块，必须定清交接棒。 | 订单贯穿三个子系统，必须明确跨子系统状态流转与字段写权限归属。 |
| 禁用模糊表述 | 发票管理目前是一个灰区。 | 发票管理目前是一项尚未明确的边界需求。 |
| 禁用空泛修辞 | 把稳财税边界，别被税拖进深水区，但要考虑票的衔接。 | 明确发票管理边界：不做税控与报税，需确认是否记录开票申请与开票状态。 |
| 禁用歧义用词 | 这里正好回扣第一份文档的决策。 | 这里对照第一份文档的决策。 |
| 减少双引号 | 它不应该只是“聊天客服”。 | 它不只是被动问答式交互。 |
| 避免名词化（中文） | 系统执行对订单数据的校验操作。 | 系统校验订单数据。 |
| 术语唯一 | 在企微里通过主 AI 大脑调用轻量化 ERP。 | 在企业微信中通过 `eoto Core` 调用 `eoto Flow`。 |
| 避免名词化（英文） | Perform a verification of the order. | Verify the order. |
| 禁用短语动词（英文） | Set up `eoto Link` and carry out a check. | Configure `eoto Link` and check the status. |

## 三、动词形式（Verb Forms）

### 1. 英文文档约束

编写英文内容时，仅允许使用以下六种动词形式：

- 不定式（例如 `to verify`）
- 祈使式（例如 `Verify the order.`）
- 一般现在时（例如 `eoto Core dispatches the task.`）
- 一般过去时（例如 `The team defined the schema.`）
- 一般将来时（例如 `eoto Cash will calculate the gross profit.`）
- 过去分词，仅用作形容词（例如 `approved terms`）

以下英文动词形式完全禁止：

- 禁止使用现在完成时、过去完成时与其他复合辅助结构。用 `We received the payment.` 替代 `We have received the payment.`。
- 禁止将 `-ing` 形式用作动词。仅允许将 `-ing` 用作既定技术名词或技术名词的一部分（例如 `accounting`、`billing`）。

### 2. 中文文档对应约束

编写中文内容时，遵守以下对应规则：

- 直接使用“主语 + 动词 + 宾语”陈述动作或结果。
- 禁止堆叠冗余体标记与空泛助动词（例如“已经完成了对……的实施”、“正在进行着……的处理”）。
- 用明确动词替代空泛动词（例如用“校验”、“创建”、“扣减”替代“进行”、“开展”、“加以”）。

## 四、语态（Voice）

1. 编写操作步骤、规范指令和开发说明时，必须使用主动语态。
2. 明确写出动作执行者（例如 `eoto Core`、`eoto Flow`、`测试 Agent`、`开发人员`）。
3. 编写描述性背景文本时，仅在动作执行者未知或与读者无关的情况下，允许使用被动语态。

### 正误示例

- **禁止**：订单状态在审批完成后被自动更新。
- **批准**：审批完成后，`eoto Flow` 自动更新订单状态。

---

## 五、句法（Syntax）

编写每一个句子时，严格执行以下六条句法限制：

1. **一句一指令**：操作说明中，每句话只表达一条指令。
2. **字词数上限**：
   - 英文程序与说明句：每句最多 20 个单词。
   - 英文描述性句子：每句最多 25 个单词。
   - 中文程序与说明句：每句最多 30 个汉字（嵌入的英文词按 1 个字词计）。
   - 中文描述性句子：每句最多 40 个汉字（嵌入的英文词按 1 个字词计）。
3. **禁止省略必要成分**：不要为了缩短句子而省略主语、动词或英文冠词。省略句子成分会产生歧义。
4. **名词串上限**：名词短语中连续堆叠的修饰名词最多包含 3 个词。超过 3 个词时，拆分为动宾结构或介词结构。
5. **完全禁用分号（STE 规则 8.1）**：正文中完全禁止使用英文分号 `;` 和中文分号 `；`。改用句号拆分为独立句子，或改用垂直列表。
6. **其他标点**：除分号外，允许使用其他标准中英文标点符号，包括破折号。

### 正误示例

- **禁止（含分号）**：`系统保留核心看板；前端不堆砌复杂表单。`
- **批准（拆分句子）**：`系统保留核心看板。前端不堆砌复杂表单。`
- **禁止（超长名词串）**：`企业全业务跨系统自动化智能协同平台底层核心引擎。`
- **批准（拆分清晰）**：`eoto Core` 协同全业务系统的底层引擎。

## 六、段落和文档结构（Paragraphs and Structure）

1. **一段一主题**：每个段落只讨论一个核心主题。
2. **句数上限**：每个段落最多包含 6 句话。
3. **强制垂直列表**：表达步骤序列、判断条件或复杂枚举时，必须使用编号列表或项目符号列表。禁止将多项并列条件埋没在长段散文中。

---

## 七、安全与高危须知（Safety and High-Risk Rules）

涉及资金流、库存扣减、权限变更、主干源码修改和合规边界的高危指令，必须遵守以下规则：

1. **命令或条件前置**：高危指令必须以明确的祈使命令或触发条件开头。禁止将禁止性要求或前提条件藏在句子中间。
2. **醒目标注**：在 Markdown 中使用加粗命令前缀（如 **严禁：**、**必须：**）或 GitHub Alert（`> [!CAUTION]` / `> [!WARNING]`）突出显示。

### 正误示例

- **禁止**：为了满足客户个性化需求，我们在交付过程中不应该直接修改底层主干源码，以免分支失控。
- **批准**：**严禁修改底层主干源码来满足单个客户的个性化需求。** 所有客户定制必须配置在 `eoto Studio` 中。

---

## 八、文档分级（Document Tiers）

项目文档分为两个级别，各级别的校验要求不同：

| 文档级别 | 存放位置 | 适用内容 | 校验要求 |
| :--- | :--- | :--- | :--- |
| 规范级文档 | `docs/`（`docs/research/` 除外）、`spec/`、`AGENTS.md`、`README.md` | 战略决策、产品定义、架构规范与契约规范 | 执行本规范全部规则 |
| 探索级文档 | `docs/research/` | 访谈记录、竞品分析与调研笔记 | 允许保留客户原话与行业惯用说法 |

编写探索级文档时，遵守以下规则：

1. 客户原话与行业惯用说法必须放在引用块（`>`）中。
2. 作者自己的分析与结论必须使用统一术语表中的标准术语。
3. 校验脚本将术语别名问题降级为警告，其他规则保持不变。
4. 探索级文档中的结论被采纳后，作者必须将结论写入规范级文档。
